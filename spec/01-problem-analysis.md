# 01 题目拆解

## 1. 一句话目标

做一个能独立运行的素材制作网站，流程是：

1. 用户浏览模板
2. 上传图片
3. 提交制作任务
4. 任务在 Java 后台分三步异步执行，期间用户可以继续用网站
5. 用户查看自己的历史记录和结果

生成过程是模拟的，耗时和成败都可以控制。

## 2. 评分重心

题目列出了这几项评价重点：

1. **后端多步骤异步处理**：受理和执行分开；每一步都有服务端可观察的边界；状态持久化；失败后中断；终态不回退。
2. **前端异步状态管理**：
   - 分清上传中、提交中、等待、处理中、成功、失败
   - 多个任务互不串扰
   - 查询异常不等于任务失败
   - 轮询能按时开始、按时停止
   - 切换用户不串数据
3. **页面与素材交互**：
   - 列表、详情
   - 上传位：预览、替换、移除、进度、失败
   - 加载中、空数据、出错时都有对应界面
4. **用户身份与个人记录**：方案合理、能演示、隔离可靠。
5. **工程交付与容器运行**：CI、关键测试、Compose 一键启动、README 完整且如实。

题目的评判倾向很明确：看重方案是否完整、可靠、讲得清楚，而不是做得有多复杂。本规格的所有取舍都以此为准。

## 3. 需求 → 验收点

每条需求怎么验证，见 06 §2 的追踪矩阵。

| 编号 | 要求 | 本方案怎么满足 |
|---|---|---|
| R-01 | 技术栈与职责 | 前端 Next.js App Router + React + TS；后端 Java + Spring Boot + MyBatis + MySQL。模板、素材、任务、个人记录的业务和持久化全在 Java。Next 只用 rewrites 转发，不含业务逻辑。版本写进 README |
| R-02 | 列表与模拟数据 | 分类导航加模板卡片（标题、封面）；按分类筛选；点卡片进详情。数据来自 `GET /api/categories` 和 `GET /api/templates`，存在 MySQL 种子数据里。模板分别需要 1、2、3 张图。封面是仓库里的本地文件 |
| R-03 | 详情、上传与提交前校验 | 详情展示标题、描述、封面、素材要求，并按 `requiredImageCount` 渲染上传位。<br>上传位支持选择、预览、替换、移除，显示上传进度和失败原因。<br>前端先校验数量、类型、大小；服务端在上传时和提交时都再校验一遍。<br>素材没齐或正在提交时，按钮禁用。<br>模板不存在、加载中、空数据、请求失败都有对应界面。<br>文件存到后端的本地卷 |
| R-04 | 受理与异步执行 | `POST /api/tasks` 校验并建好记录后返回 202 和任务 ID。后续步骤在 Java 线程池里执行，与 HTTP 请求无关，关掉页面也不影响。worker 数可配，多任务排队执行 |
| R-05 | 多步骤状态与查询 | 素材检查 → 模拟生成 → 结果整理，每一步写一条步骤记录（开始时间、结束时间、结果）。任务表保存当前阶段、状态，以及结果地址或失败原因。查询接口只读。所有状态更新都带 SQL 守卫，终态不回退 |
| R-06 | 失败与模拟控制 | 开发接口可以指定失败阶段，重置前一直生效，可重复触发。失败后不再执行后续步骤，并保存失败阶段和中文原因。各步耗时可以用环境变量或开发接口调整 |
| R-07 | 状态表达与请求异常 | 界面能分清：上传中、提交中、等待处理、处理中（显示当前阶段）、成功（显示结果）、失败（显示阶段和原因）。任务受理后按钮立刻恢复。查询失败时保留已有信息，并提供"重新查询" |
| R-08 | 多任务与查询生命周期 | 可以连续创建多个任务，彼此独立。只轮询未完成的任务，结束就停；没有未完成任务时一个请求也不发。离开页面或切换用户时，取消请求并清空缓存 |
| R-09 | 刷新恢复与结果记录 | 历史记录（创建时间、状态、结果或失败原因）从后端读取。刷新后继续跟踪未完成的任务。成功的结果可以预览大图 |
| R-10 | 用户身份与个人记录 | 用户名 + 密码登录，会话放在 HttpOnly Cookie 里；预置演示账号，也可以注册。任务、素材、结果按用户隔离。账号弹窗参考截图。README 写明方案和演示方法 |
| R-11 | 参考界面与交互 | 深色风格，列表、详情、历史的布局参照截图。小屏也能操作。按钮、输入框、对话框语义正确；保留键盘焦点；上传位和图标按钮都有可理解的标签 |
| R-12 | CI 与关键测试 | GitHub Actions 在 push 和 PR 时运行前端的 lint、类型检查、测试、构建，以及后端的测试和构建。测试重点：后端的步骤顺序与失败中断；前端的多任务不串扰、查询异常与任务失败的区分 |
| R-13 | 提交材料与说明 | 完整源码、锁文件、表结构和初始化数据、CI、包含九项内容的 README、验收 commit |
| R-14 | 容器交付 | `docker compose up --build` 启动前端、后端和 MySQL，并自动完成初始化；附 Dockerfile 和 `.env.example` |

## 4. 红线（出现即严重缺陷）

1. 提交接口同步跑完整个流程，或者前端定时切换文案来冒充后台步骤。
2. 查询接口推进任务，例如每查一次就走一步。
3. 已结束的任务变回处理中，不管是后端更新造成的，还是前端合并数据造成的。
4. 查询失败被显示成任务失败。
5. 某一步失败后，后续步骤仍然执行。
6. 能看到或访问别人的任务、素材、结果。
7. 用浏览器的临时地址（blob:）代替服务端素材。
8. 没有未完成任务时还在轮询，或者离开页面后请求还在跑。
9. `docker compose up --build` 起不来。

## 5. 范围

### 做

第 3 节的全部验收点，再加上：

- 启动时的最低限度恢复：排队中的任务继续执行；执行到一半的任务标记为"服务重启中断"
- 查询接口故障模拟开关，用来演示 R-07
- 提交幂等键（P1）

### 不做

- 真实 AI、支付、积分和会员（截图里的 credits、Manage Billing 都不做）
- 模板管理后台、国际化（截图里的 English 切换不做）、第三方登录
- 删除、下载、重新制作、自动重试、断点续跑
- 多实例部署（只在 README 里说明扩展思路）

### 为什么不加 RocketMQ / Redis

结论：一天的工期里不加。把扩展口子留好，在 README 里讲清楚。

1. **题目不需要**：题目写明不强制消息队列和 Redis，"集群与消息队列运维"也不在范围内。
2. **增加启动风险**：评审会在隔离的容器环境里执行 `docker compose up --build`。
   - RocketMQ 至少要多出 NameServer 和 Broker 两个容器。
   - Broker 默认内存占用大、启动慢。
   - `brokerIP1` 配错，客户端就连不上。

   多一个服务，就多一个起不来的可能。
3. **版本不匹配**：官方的 `rocketmq-spring-boot-starter` 最新版是 2.3.6，仍然基于 Spring Boot 2.7.18 / Spring 5.3 构建（2026-11-10 查 Maven Central），和 Boot 4.1 / Spring 7 对不上。如果绕开 starter 直接用客户端，就要多写一套生产者、消费者和测试替身。
4. **价值可以用设计体现**：
   - 派发抽象成 `TaskDispatcher` 接口。
   - worker 用 `UPDATE … WHERE status='PENDING'` 抢占任务，即使消息重复投递，任务也只执行一次。

   所以要换成 RocketMQ，只需新增一个实现，消息体就是 taskId。
5. **Redis 没有合适的位置**：
   - 会话存在 MySQL 就够了。
   - 模板只有十来条，不需要缓存。
   - 给任务状态加缓存反而可能读到旧值，正好违反"完成后不能变回处理中"。

如果全部完成后还有富余时间，可以再讨论以 compose profile 的方式加一个可选的 MQ 派发器，默认关闭。

## 6. 容易读错的地方

| 题目说法 | 本方案的理解 |
|---|---|
| 多任务可以排队或并行 | 两种都行。worker 数可配：默认 2，设成 1 就能看到排队 |
| 当前阶段与整体状态可以分别设计 | 分开设计：`status`（4 个值）+ `stage`（3 个值）+ `failedStage` |
| 不需要随机失败 | 失败注入是确定的：指定一个阶段，重置前一直生效 |
| 关闭页面不应中断任务 | 任务在后台线程执行，和浏览器连接无关 |
| 查询接口暂时不可用属于请求异常 | 前端必须和任务失败分开显示。另外提供开发开关，让查询接口返回 503，方便演示 |
| 离开页面或切换用户时妥善清理 | 组件卸载时停止轮询并取消请求；查询 key 带 userId；切换用户时取消全部请求并清空缓存 |
| 截图中的题外功能不扩展要求 | credits、English、Billing、Delete Account、卡片上的删除按钮都不做 |
| 服务重启后自动恢复执行不要求 | 只做最低限度：排队中的任务继续执行；执行到一半的任务标记为失败，并写清原因 |
